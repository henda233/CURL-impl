# 训练日志记录 —— 开发复盘

## 一、开发内容概述

### 1.1 任务背景与目标

需求《训练日志记录.md》：ac 与 sac 训练过程中仅保留 eval 的 json 结果，没有保存全部输出。要求向两个算法的训练代码增加训练日志保存：训练日志指控制台输出的所有内容，以 txt 保存至对应运行目录 `data/.../train_log.txt`。

该特性为横切改造：ac 与 sac 的 `train.py` 结构一致（目录创建后打印 out/cfg、逐 episode 进度、EVAL 节点、DONE），日志机制需同时接入两算法并保持平行结构。交付目标是"所见即所得"——文件内容与控制台输出一致，正式、smoke、profile 运行一视同仁。

任务按仓库惯例纳入文档体系：需求落 `docs/functions/训练日志记录.md`，技术文档与复盘文档分别落 `docs/techs/` 与 `docs/notes/`，与既有算法特性的三件套结构一致；本特性改动量小，两份文档篇幅亦相应收敛。

### 1.2 与用户对齐的决策（文字问答，多轮收敛）

第一轮四问拍板：

1. **内容口径 = 原样照录**：不加时间戳或分段标题，txt 与终端逐字一致。
2. **机制 = 程序内 tee 双写 stdout 与 stderr**：控制台与文件各写一份，第三方库警告与 traceback 一并入档。
3. **组织 = 平行复制**：`src/ac/` 与 `src/sac/` 各放同构 `log_tee.py`，不抽跨算法共享模块。
4. **生命周期 = 目录创建起记录至进程结束、逐条 flush、追加写入**。

第二轮三问拍板：范围仅两个 `train.py` 与新增小模块（`eval_demo.py` 不动）；`train_log.txt` 用追加模式与 `eval_history.jsonl` 对齐；讨论收敛后直接实现并以 ac、sac 各一次 smoke 验收，技术文档与 MEMO/USER 更新留待收尾统一进行。

### 1.3 过程记录

任务以"读需求、多轮讨论、拍板实现"推进，未经历代码 bug 修复期。两轮提问共七问，用户均选择推荐项中保守、可逆的方案，与既有决策风格一致。进入实现后一次成型：先写 `log_tee.py`（`cp` 复制保证逐字节同构）、再接两个 `train.py`、最后本机验证。临时验证脚本置于 `data/`（已 gitignore）用后即删，不污染仓库。

### 1.4 交付物与验收口径

| 文件 | 改动 |
|---|---|
| `src/ac/log_tee.py`、`src/sac/log_tee.py` | 新增，逐字节同构（约 60 行）：tee 流替换 stdout/stderr，`start`/`stop` 幂等 |
| `src/ac/train.py`、`src/sac/train.py` | 各两处接入（`import log_tee`、mkdir 后 `start`、DONE 后 `stop`）并更新 docstring，行级 diff |

验收（数据导向）：ac、sac 各跑 `--smoke`，`train_log.txt` 与重定向捕获的终端输出逐字一致、退出码 0；附加单测覆盖 stderr 捕获、追加语义与中断兜底。

## 二、开发决策

### 2.1 机制取舍：为何 tee 而非 logging 或 shell 重定向

需求口径是"控制台输出的所有内容"，这决定了机制。三候选对比：

| 候选 | 覆盖范围 | 改动量 | 落盘方式 |
|---|---|---|---|
| 程序内 tee | stdout/stderr、第三方输出、traceback 全量 | 模块约 60 行 + 每算法两处接入 | 自动按运行目录 |
| logging 重构 | 仅自身 print | 全部 print 改 logger 并逐处配置 | 自动 |
| shell 重定向 | 全量 | 零代码 | 手动，依赖调用者每次执行 |

logging 重构捕获不到第三方库直写 stdout/stderr 的警告与 traceback，与"全部输出"口径不符且改动面大；shell 重定向无法按运行目录自动落盘，不满足"向训练代码增加设计"的意图。选 tee。代价是替换全局流需谨慎：`_Tee` 须委托 `isatty`、`fileno`、`encoding` 等属性，避免依赖流属性的第三方代码行为漂移；`flush` 需转发原流以维持原缓冲策略。

### 2.2 组织取舍：平行复制而非共享模块

仓库现状是 ac 与 sac 目录自治、历次改动以复制同步，无跨算法共享运行时代码；且 `train.py` 以脚本方式运行，`sys.path` 只含脚本目录，抽共享模块需额外引入路径机制。权衡后选平行复制：改动透明、不引入新加载机制。代价是两份实现未来可能漂移；机制体量小，漂移风险可控，CURL 阶段接入第三个算法时可再评估是否抽共享。

### 2.3 生命周期实现：逐条 flush 替代 try/finally 整体缩进

将训练主循环整体包入 `try/finally` 需缩进约百行、diff 可读性差。改为：正常收尾在 DONE 后显式 `stop()`；异常与 Ctrl+C 路径不显式 stop，依赖两层保障——逐条 flush 消除缓冲滞留、模块全局持有文件句柄直至解释器退出时统一清理。未捕获 KeyboardInterrupt 的 traceback 打印发生在进程退出前，经 stderr tee 已入档。该取舍以实测确认（见三）。

### 2.4 其余约定

- **追加模式**：与 `eval_history.jsonl` 一致；时间戳到秒，极端同秒复用目录时两段运行衔接保留。
- **模块命名**：沿用 MEMO 中 profile.py 遮蔽 stdlib 的教训，`log_tee` 无标准库同名。
- **编码**：日志文件固定 utf-8，不随 Windows 控制台 locale；日志内容以 ASCII 为主，无编码风险面。
- **平台无关**：tee 仅依赖标准流替换，不引入平台特性，GPU/Linux 主机无需改动。

### 2.5 接入顺序的推敲

`start` 必须位于目录创建之后、首个 print（out= 行）之前：目录未建则无落盘路径，晚于首行则 out 与 cfg 两行配置输出丢失，日志残缺。`stop` 必须位于 DONE 行之后，保证收尾摘要入档。两处调用均为毫秒级操作，不扰动训练时序；该顺序在 diff 中以各两行增量体现，代码评审易于核对。

## 三、实测结果（本机自证）

验证在仓库根目录以 `.venv` CPU 解释器执行：ac smoke（600 环境步）与 sac smoke（120 环境步、batch 16）均在数十秒内完成，加上两次机制单测，整个验收约数分钟，符合本机快速验证的节奏；耗时剖析类验证按惯例留给 GPU 主机。

### 3.1 验证方法与口径

比对方法：进程 stdout 与 stderr 合并重定向至临时文件（shell `2>&1`），与 `train_log.txt` 各自去除行尾 `\r`（Windows 文本流换行转换）后逐行 diff。比对口径为"内容全集与行序一致"——管道重定向下 stdout 块缓冲可能使终端跨流显示乱序，文件按程序 write 调用顺序记录，两者内容全集相同即可，不要求与终端显示逐字节同步。

### 3.2 训练链路 smoke

ac 与 sac `--smoke` 各一次，退出码 0，diff 零差异。ac 日志五行：

```
[ac-train] out=...\data\ac-20260908-112046-smoke
[ac-train] cfg device=cpu seed=0 max_env_steps=600 ...
[ac-train] ep=1 env_steps=600 ep_return=38.245 ...
[ac-train] EVAL env_steps=600 mean_return=43.788 ...
[ac-train] DONE env_steps=600 episodes=1 ...
```

sac 日志同样五行为 out、cfg（含 profile=False 与 SAC 超参）、ep、EVAL、DONE：

```
[sac-train] ep=1 env_steps=120 ep_return=10.701 ...
[sac-train] EVAL env_steps=120 mean_return=18.455 ...
[sac-train] DONE env_steps=120 episodes=1 ...
```

日志自首个 `out=` 行起完整覆盖训练全程，逐字一致通过。

### 3.3 机制单测

- **stderr 与追加**：临时脚本两次 `start` 同一文件并写入 stderr 行，最终内容依次为 `first-line`、`stderr-line`、`second-line`，确认 stderr 入档与追加语义。
- **中断兜底**：`start` 后打印两行再 `raise KeyboardInterrupt`，退出码 130，日志保留两行与完整 traceback，验证不显式 `stop()` 路径不丢内容。

## 四、复盘要点

本特性未产生真实代码 bug，但有三处边界认知值得记录：

1. **终端显示序与文件记录序的差异**：管道重定向下 stdout 块缓冲、stderr 无缓冲，终端可能出现跨流乱序；文件按程序 write 调用顺序记录。验收口径据此定为内容全集一致而非逐字节同步，避免把缓冲行为当成缺陷误判。
2. **目录创建前的输出不可入档**：argparse、import、环境构建先于 `out_dir` 存在，属结构性边界，实现前已与用户对齐接受。
3. **全局持有文件句柄的兜底价值**：不显式 `stop()` 的路径安全，前提是模块全局引用文件对象、避免提前被垃圾回收；若改为局部引用则退出期输出可能写入已关闭文件。

## 五、经验与衔接

- 横切小机制（约 60 行）选"平行复制 + 收尾统一文档"，对低代码量特性而言改动透明、验收直接，工程开销低于抽象共享模块；是否抽共享以出现第三份复制为触发信号。
- 替换全局流的通用做法沉淀为检查清单：委托流属性（isatty/fileno/encoding）、flush 转发、模块级持有句柄、命名避开 stdlib、文件编码固定。
- 后续衔接：改动未 git 提交，提交与 GPU 实机复验由用户安排；技术文档 `docs/techs/训练日志记录技术文档.md` 与复盘本文已产出，MEMO 的"当前任务/历史任务"更新并入本次特性收尾统一执行。
